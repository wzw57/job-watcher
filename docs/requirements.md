# 需求规格说明

## 1. 项目目标

本项目是面向个人使用的青岛国企/央企 2027 秋招信息汇总与求职助手。

项目核心目标是建立一个可持续运行、可核实、可展示、可推送的招聘信息中枢，重点关注：

- 青岛地区国企、央企驻青岛单位、山东/青岛相关央企岗位。
- 2027 届秋招、校招、管培、提前批、宣讲会、招聘公告。
- 泛计算机岗位，尤其是网络安全、信息安全、数据安全、信息技术、软件、数字化、运维等方向。

项目核心不依赖大模型。大模型只用于辅助抽取、摘要、相关性判断和后续自然语言交互。

## 2. 用户与使用场景

### 2.1 用户

当前仅面向一个用户使用。

用户需要：

- 持续发现国企/央企招聘信息。
- 管理企业名单和招聘入口。
- 每天看到新增动态。
- 对不可信来源进行人工确认。
- 后续管理投递、面试、笔试、测评和邮箱通知。

### 2.2 核心使用场景

1. 用户导入本地企业表。
2. 系统清洗企业数据并拆分候选 URL。
3. 系统检测 URL、生成修正队列。
4. 系统通过搜索 API 补充候选官网、招聘入口、公告来源。
5. 用户在看板中确认可信来源。
6. 系统只对可信来源做后续监控。
7. 系统发现招聘线索后入库、展示并推送飞书。
8. 用户在看板中标记投递进度和下一步任务。

## 3. MVP 范围

### 3.1 MVP 必须包含

#### 企业数据管理

- 导入 `青岛国企.xlsx` 清洗后的企业种子数据。
- 保留原始企业名、集团、区域、优先级、推荐方向、原始 URL。
- 支持企业核实状态。
- 支持 P0/P1/P2/P3/P4 优先级筛选。

#### 来源管理

- 导入表格拆分出的候选 URL。
- 导入固定公共信息源配置。
- 管理来源类型：
  - official
  - official_recruitment
  - government
  - public_platform
  - campus
  - commercial_platform
  - search
  - manual
- 管理来源状态：
  - candidate
  - verified_official
  - verified_recruitment
  - verified_government
  - verified_platform
  - needs_search
  - needs_browser
  - invalid_replaced
  - invalid_unresolved

#### 数据核实与修正

- 对候选 URL 做可限量、可恢复的核验。
- 对错误、超时、无关、低权威来源生成修正队列。
- 支持知乎、百度、博查、人工搜索结果进入统一搜索结果格式。
- 对搜索结果打分并生成修正候选。
- 支持人工确认候选来源。

#### Web 看板

第一版看板至少包含：

- 企业库视图。
- 候选来源视图。
- 修正候选视图。
- 已确认来源视图。

看板必须支持：

- 筛选。
- 排序。
- 查看详情。
- 修改状态。
- 添加备注。
- 确认或拒绝候选来源。

#### 数据库存储

- 使用 SQLite。
- 支持重复导入时更新而不是重复插入。
- 支持后续迁移 PostgreSQL。

#### 基础配置

- API key 只通过环境变量读取。
- 不把 key 写入代码、文档、CSV 或配置文件。
- 提供 `.env.example`。

### 3.2 MVP 不包含

第一版暂不实现：

- QQ 邮箱接入。
- 日历同步。
- 飞书双向聊天。
- 大模型自动对话助手。
- 全站 Playwright 爬取。
- 大规模招聘网站爬取。
- 多用户账号系统。
- 权限分组。
- 移动端独立 App。

这些功能作为后续阶段实现。

## 4. 功能需求

### 4.1 企业导入

输入：

- `data/processed/companies_seed.csv`
- `data/processed/company_sources_seed.csv`
- `config/sources.yaml`

输出：

- `companies`
- `sources`

要求：

- 支持幂等导入。
- 支持按 `company_key` 更新。
- 支持一家公司多个来源。
- 原始字段和标准化字段都要保留。

### 4.2 来源核实

系统应支持：

- HTTP 状态检测。
- 页面标题提取。
- 判断是否 JS 外壳。
- 判断是否低权威来源。
- 标记 `needs_browser`、`needs_search`、`blocked`、`timeout` 等状态。

注意：

- `timeout` 不等于 URL 错误。
- 国内站点在本机或海外 VPS 上可能因为网络导致超时。
- 不可访问来源应优先进入搜索修正，而不是直接删除。

### 4.3 搜索修正

系统应支持搜索 Provider：

- Zhihu global_search。
- Baidu web search。
- Bocha web search，额度可用时启用。
- Manual import。

搜索结果统一字段：

- `task_id`
- `company_key`
- `company_name`
- `query`
- `provider`
- `rank`
- `title`
- `url`
- `snippet`

搜索结果进入打分流程，不直接进入可信来源。

### 4.4 人工确认

用户可以对修正候选做以下操作：

- `accept_official`
- `accept_recruitment`
- `accept_government`
- `accept_platform`
- `accept_reference`
- `reject`
- `needs_more_search`

确认后生成或更新可信来源。

### 4.5 后续招聘监控

MVP 只需为招聘监控预留数据结构。正式监控在下一阶段实现。

预留能力：

- 快照表。
- 招聘线索表。
- 来源最新检查时间。
- 来源抓取状态。

## 5. 非功能需求

### 5.1 稳定性

- 不依赖单一搜索 API。
- 不依赖大模型 Agent 作为主流程。
- 每个外部请求必须有超时。
- 批量任务必须可恢复。

### 5.2 成本

- 默认只处理 P0/P1。
- 搜索 API 低频使用。
- 大模型默认关闭。
- VPS 上不常驻浏览器。

### 5.3 可追溯性

每次修正应记录：

- 原始 URL。
- 候选 URL。
- 来源 Provider。
- 查询词。
- 评分原因。
- 人工确认状态。
- 确认时间。

### 5.4 安全

- API key 不落盘。
- 邮箱授权码后续必须只放环境变量。
- Web 看板后续上线 VPS 时必须有访问保护。

### 5.5 可部署性

- 本地 Windows 可运行。
- Rocky Linux VPS 可运行。
- 第一版不依赖 Docker。
- SQLite 数据库可备份。

## 6. 验收标准

MVP 完成时应满足：

1. 能导入 500 条企业数据。
2. 能导入 690 条候选来源。
3. 能导入固定公共信息源。
4. Web 看板能展示企业和来源。
5. Web 看板能确认或拒绝修正候选。
6. 确认后的来源能进入可信来源列表。
7. 搜索结果和人工确认过程可追溯。
8. 所有密钥通过环境变量传入。
