> 项目仓库：`wzw57/job-watcher`  
> 当前开发分支：`agent/v1-data-foundation`  
> 当前草稿 PR：`#1 Build V1 data and collector foundation`
> 文档用途：作为 Codex 网页版、后续开发者和项目维护者的唯一开发基线。

## 1. 项目定位

秋招雷达是一个面向个人使用的青岛求职情报系统。它不是通用招聘网站，核心目标是：

1. 尽早发现青岛范围内适合用户的招聘机会；
2. 尽量降低国企、央企、银行、事业单位和外企招聘的遗漏；
3. 明确展示哪些企业和渠道已被有效监控，哪些仍存在覆盖缺口；
4. 保留每条招聘信息的原始来源和证据；
5. 支持筛选、标记、人工核验、投递管理和每日简报。

系统采用高召回策略：可以多收信息，但不能静默漏采，也不能把搜索摘要或社区线索伪装成已经核实的官方招聘。

## 2. 用户与求职范围

- 2027 届网络空间安全硕士；
- 地域以青岛为核心，山东和全国可选岗位作为补充；
- 首选青岛国企、央企驻青机构、银行、事业单位、政府技术支撑单位；
- 第二重点为青岛全部外企，包括小型分支、工厂、研发中心和办事处；
- 岗位采用宽口径，不限于“网络安全工程师”；
- 应覆盖信息安全、安全运营、数据安全、科技风险、信息化、系统运维、数字化、技术项目管理、合规、技术支持、解决方案、售前和适合硕士的职能岗位；
- 宁可多收，由用户筛选，不要过早自动删除低匹配信息。

## 3. 核心设计原则

### 3.1 主体、渠道、证据和招聘事件分离

- `companies`：谁可能招聘；
- `sources`：在哪里发布招聘；
- `raw_items`：每个来源具体采集到了什么；
- `job_events`：多个来源归并后，用户最终看到的一次招聘；
- `job_positions`：招聘事件内的具体岗位；
- `applications`：用户的投递进度；
- `review_tasks`：自动化无法确认的问题。

任何新功能不得绕过原始证据层直接生成不可追溯的招聘事实。

### 3.2 搜索引擎是一等数据源

搜索引擎不是临时补漏按钮，而是持续运行的主动发现管线，承担：

- 新招聘发现；
- 新企业、新分支和新研究院发现；
- 新官网、新招聘入口和公众号发现；
- 固定渠道失效后的替代来源搜索；
- 对政府网站、大学就业网等站点的定向检索。

搜索结果必须保存查询词、引擎、排名、标题、摘要、URL、首次发现时间和最后出现时间。搜索摘要只属于线索，不等于正式招聘事实。

### 3.3 覆盖必须可审计

覆盖状态至少分为：

1. 名义覆盖：保存了 URL；
2. 技术覆盖：采集器可访问；
3. 解析覆盖：能提取正文和附件；
4. 有效覆盖：近期验证正常；
5. 多源覆盖：官方源之外还有可信补充源。

“没有新招聘”和“采集失败”必须严格区分。

### 3.4 自动化与人工核验闭环

公众号、验证码页面、地点不明确、集团归属、劳务派遣、社区线索等问题必须进入 `review_tasks`，不能静默丢弃或自动猜测。

## 4. 目标主体分层

### 4.1 第一层：核心必监控

- 青岛市属、区属国企及各级子公司；
- 山东省属国企驻青主体；
- 央企驻青子公司、分公司、研究院和区域总部；
- 银行、保险、证券、担保、资管和金融科技机构；
- 事业单位、高校、科研院所、医院信息化岗位；
- 电网、烟草、铁路、邮政、运营商等特殊体系；
- 政府直属信息化、网信、数据和应急技术支撑单位。

### 4.2 第二层：青岛外企

- 青岛独立外资法人；
- 外企青岛分公司和办事处；
- 外资工厂、研发中心和区域总部；
- 中外合资、外资控股企业；
- 招聘由全国总部发布但工作地点在青岛的企业。

外企主体发现需要结合企业登记、商务部门、开发区名录、商会会员、产业园区、招聘历史和全球办公地点。

### 4.3 第三层：扩展机会池

- 青岛上市公司和优质民企；
- 国企数字科技、工业互联网和数据运营子公司；
- 汽车供应链、咨询、认证、检测和技术服务企业；
- 工作地点写山东或全国分配但可能落地青岛的岗位。

## 5. 信息源体系

### 5.1 官方渠道

- 企业招聘官网；
- 企业官网招聘栏目；

### 5.2 权威转发和公共平台

- 各大学就业信息网；
- 国家大学生就业服务平台；
- 国聘；
- 地方政府人才和公共招聘网站；
- 高校人才网等同类网站。

### 5.3 商业平台与社区

- BOSS 直聘、智联、前程无忧、猎聘、实习僧、应届生等；
- 牛客、Offershow、脉脉、小红书、知乎等社区。

社区来源默认只作为待核验线索。

### 5.4 搜索引擎

- 百度、必应、搜狗、Google 等通用搜索；
- 招聘网站、学校就业网等站内搜索；

### 5.5 外部人工数据

后续接入第三方维护的腾讯表格。必须先进入临时导入区，执行字段映射、主体匹配、冲突检查和去重，再进入正式表；外部删除不得自动删除正式数据。

## 7. 技术架构

### 7.1 当前建议

- Python 3.11+；
- SQLite 起步，后续可迁移 PostgreSQL；
- 当前 Web 使用 Python 标准库页面；
- 后端最终采用 FastAPI；
- 第一版界面可以继续服务端渲染，稳定后再决定是否使用 React；
- 动态页面采用 Playwright；
- 通用采集优先考虑 Crawlee Python；
- 网页正文使用 Trafilatura；
- PDF、DOCX、XLSX 和图片解析使用 Docling 或轻量解析库；
- changedetection.io 可作为独立页面变化服务接入，避免复制全部变化监控能力。

### 7.2 推荐模块

```text
src/job_watcher/
├── api/                 # FastAPI 接口
├── storage/             # 数据库、迁移和仓储
├── importers/           # Excel、CSV、腾讯表格导入
├── collectors/
│   ├── http.py          # 静态页面
│   ├── browser.py       # Playwright
│   ├── search/          # SearchProvider
│   └── adapters/        # 特定站点适配器
├── parsers/
│   ├── html.py
│   ├── document.py
│   ├── recruitment.py
```

## 8. 数据模型要求

### 8.1 企业主体

必须支持：标准名称、简称、别名、直接上级、根集团、主体类型、所有制、行业、区市、青岛关系、统一社会信用代码、官方域名、优先级、监控状态、证据级别和最后核验时间。

### 8.2 渠道

必须支持：所属企业、来源类型、来源级别、URL、公众号账号信息、监控方式、内容类型、调度周期、历史活跃月份、核验状态、健康状态、连续失败次数和解析器。

### 8.3 原始记录

每个来源的一条结果保存 URL、规范化 URL、标题、正文、附件、内容哈希、发布时间、发现时间、采集状态、解析状态、可信度、元数据和归并状态。

### 8.4 招聘事件和岗位

招聘事件保存招聘主体、发布主体、用工主体、签约主体、届别、地点、青岛关系、发布时间、截止时间、报名入口、用工性质、可信度和匹配评分。具体岗位拆分到 `job_positions`。

### 8.5 投递和核验

投递状态：待判断、准备投递、已投递、笔试、面试、等待结果、Offer、淘汰、放弃。不得保存明文密码。

核验类型至少包括：新主体、企业归属、青岛关系、新渠道、公众号、页面失效、解析失败、疑似重复、届别和地点不明、劳务派遣、社区线索。

## 9. 采集管线

```text
调度任务
  -> HTTP/浏览器/搜索/人工导入
  -> raw_items
  -> 正文和附件解析
  -> 招聘分类
  -> 企业识别
  -> 字段提取
  -> 候选事件检索
  -> 自动归并或人工核验
  -> job_events + job_positions
  -> 匹配评分
  -> 今日雷达/每日简报
```

采集状态至少区分：成功有内容、成功无新增、解析失败、结构变化、需要 JavaScript、需要登录、验证码、请求拒绝、域名失效和临时网络错误。

HTTP 失败后可降级为浏览器渲染，再降级为搜索转载，最终生成核验任务。连续失败不能无限重试。

## 10. 搜索任务设计

搜索任务分为：

1. 全局招聘发现；
2. 企业定向招聘搜索；
3. 政府、大学就业网等来源定向搜索；
4. 新企业、新分支、新外企发现；
5. 新官网、新招聘入口和公众号发现；
6. 失效渠道恢复搜索。

应按企业优先级、历史招聘窗口和秋招季节调整频率。S 级主体高峰期每日多次，A 级每日，B 级每数日，C 级每周或按需。

## 11. 公众号策略

公众号采用半自动方案：

- 保存公众号名称、微信号、认证主体和历史招聘月份；
- 搜索公开索引、转载和企业名加招聘关键词；
- 支持用户粘贴文章 URL、正文或上传附件；
- 生成每日/每周人工检查任务；
- 记录最后人工检查时间；
- 不把“保存了公众号名称”算成有效内容覆盖。

不要在第一阶段承诺微信公众号完全自动化。

## 12. 去重和归并

同一公告在多个网站出现时，`raw_items` 保留多条，`job_events` 只保留一个事件，并展示全部来源。

建议归并评分：主体一致 25、标题相似 20、批次一致 15、发布时间接近 10、截止日期一致 10、报名 URL 一致 10、岗位列表相似 10。

- 85 分及以上自动合并；
- 60–84 分进入人工核验；
- 低于 60 分创建新事件。

集团同批次的不同子公司岗位可以关联但不能错误合并。

## 13. 个人匹配

评分维度：青岛地点、2027 届、硕士、专业范围、岗位方向、企业优先级、党员/户籍/经验限制、截止紧迫度和用工性质。

匹配结果：强匹配、值得查看、可能可投、条件不明、明显不匹配。低分信息保留，默认不自动删除。

## 14. 页面与交互

### 必须页面

1. 今日雷达：今日新增、即将截止、高匹配、异常渠道、待核验；
2. 招聘事件库：通用筛选、标记、全部来源 URL；
3. 企业主体库：集团树、属性、优先级、历史招聘；
4. 覆盖中心：名义/技术/解析/有效/多源覆盖；
5. 投递管理；
6. 人工核验中心；
7. 每日简报；
8. 搜索任务和搜索结果管理。

### 通用操作

- 搜索、筛选、排序；
- 已读、收藏、忽略、值得投递、信息存疑；
- 批量标记；
- 查看全部来源和原始快照；
- 快速创建投递记录；
- 快速解决人工核验任务。

## 15. 分阶段开发计划

### 阶段 A：完成数据底座迁移（代码与当前数据包已验收）

- 合并并完善 PR #1；
- 为新模型补充仓储层和状态枚举；
- 编写从 `job_leads` 到 `raw_items/job_events` 的迁移命令；
- 增加约束、索引和测试；
- 验证 500 企业、690 企业来源及 15 固定公共源不丢失。

验收结果：真实 seed manifest、字段、跨文件 key 和 SHA-256 校验通过；重复导入后仍为
500 企业、705 总来源；旧数据迁移可重复执行，外键无违规，新旧数据通过 legacy id 可追溯。

### 阶段 B：采集器重构（已验收）

- 建立统一 Collector 接口；
- HTTP 采集写入 `source_runs` 和 `raw_items`；
- 引入正文提取；
- 处理 PDF、Word、Excel 和图片附件；
- 保留原始快照；
- 失败自动生成核验任务。

当前已完成统一 `Collector/CollectionResult` 契约、HTTP Collector、`source_runs` 运行记录、
`raw_items` 证据写入、内容未变化识别、来源健康更新，以及 blocked/needs_browser/
parse_failed/http_error/network_error 的人工核验闭环；同时支持 HTML 附件发现，PDF、DOCX、
XLSX、CSV 文本提取和附件级 `raw_items`，附件失败使用 `partial_success` 与核验任务表达。
现已增加 main/article 优先正文抽取、导航噪声过滤、有限重试、响应与附件数量限制、附件
原文件按哈希持久化、单 URL 诊断命令，以及可选 Playwright 浏览器降级链路。固定验收池
包含 22 个政府、高校、平台、企业和文档样本，可并发运行并输出 JSON 报告；正文质量分
低于阈值时保留证据并进入人工核验。扫描 PDF 明确标记 `ocr_required`，旧 DOC/XLS 标记
`legacy_office_conversion_required`，作为后续可选 OCR/格式转换服务的稳定接口。

验收结果：23 项单元测试通过；22 个政府、高校、平台、企业和文档真实样本严格验收
22/22 符合预期；采集成功、HTTP 错误、访问阻断、需要浏览器和网络错误均能明确区分并保留证据。

### 阶段 C：招聘归并与匹配

- 招聘分类和字段提取；
- 企业别名匹配；
- 去重评分；
- 人工归并界面；
- 个人匹配评分和理由。

验收：同一公告多站转载只显示一个招聘事件，全部来源仍可查看；不同子公司不会被误合并。

当前实施基线见 `docs/stage_c_implementation_plan.md`。必须先完成纯数据解析契约、固定样本和
幂等处理链路，再更新页面。低质量正文、泛招聘入口、搜索摘要和主体歧义不得直接创建正式事件。

### 阶段 D：覆盖中心和主体发现

- 企业集团树；
- 渠道健康检查；
- 五级覆盖指标；
- 新主体、新分支和新外企发现；
- 待穿透主体队列。

验收：任何核心主体都明确显示已覆盖、部分覆盖或未覆盖，并能看到缺失原因。

### 阶段 E：搜索与公众号

- 统一 SearchProvider；
- 多搜索引擎任务；
- 搜索结果去重和时间判断；
- 公众号半自动任务；
- 手动 URL/正文/文件收录。

验收：主动搜索可持续产生招聘、渠道和新主体三类候选；搜索接口失败不会显示为空成功。

### 阶段 F：投递、简报和部署

- 投递状态机和提醒；
- 每日简报；
- 秋招高峰调度；
- Docker/VPS 部署；
- 日志、备份和健康检查。

验收：服务重启后任务和数据不丢失；每天能生成带来源链接的简报；数据库可恢复。
